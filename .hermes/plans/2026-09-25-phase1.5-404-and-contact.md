## 3. D1 — `404.html`

New file at repo root. Cloudflare Pages serves the closest `404.html` with a **404 status** once it exists (docs: "Not Found behaviour").

- Standalone page, same head pattern as other static pages (GA snippet, privacy-banner.js), `<meta name="robots" content="noindex">`, no canonical.
- Content: 404 headline, "The page you're looking for doesn't exist (or moved).", links: `Browse all restaurants` → /restaurants · `Own a restaurant? Find your listing` → /claim/ · `Home` → /, plus "Think this link should work? hello@thaidata.uk".
- Cache: covered by the existing `/*.html` `_headers` rule (max-age=600). No `_headers` change needed.
- **Middleware audit (done, no change needed):** `functions/r/_middleware.js` guards both of its asset checks for either a non-ok response **or** a missing marker (`Hygiene` / `thaidata-page`), so it is unaffected by the change — /r/ 404s stay as-is, including the claim-source variant.
- After shipping: `/contact` will briefly 404 until D2 lands — accepted (today it wrongly serves the homepage).

**Tests:** new `tests/test_static_pages.py` → `404.html` exists, has `noindex`, links to `/`; plus live check in §8.

## 4. D2 — `/contact` page (FAQ-first)

New `contact.html` at repo root (Pages serves it at `/contact`, same as /about).

Structure (skeleton copied from `about.html`; self-contained CSS like the other static pages):

1. **Header/lead:** "How can we help?" + one-line intro.
2. **FAQ block** (`.faq-item` pattern, click-to-expand — copy of claim page's pattern), 6 items:
   - How do I claim my restaurant's listing? → free; 48h verification; link /claim/.
   - Something on my listing is wrong — what should I do? → fastest: your restaurant's page → "Spotted a mistake?"; anything else: form below.
   - Where does your restaurant data come from? → FSA registers, weekly refresh; link /data-quality.
   - Can I have my restaurant removed or updated? → message us; we action manually.
   - How quickly do you reply? → "usually within a few hours on weekdays — every message is read by a human."
   - Press, data requests, anything else? → same form.
3. **Form** under a "Still need help? Send a message" fold:
   - Fields: `#contact-message` (required, 10–2000), `#contact-email` (optional), honeypot `input name="website"` (`.hp-field`), submit, `#contact-status` (role=status). No name field (fewer fields = more submissions).
   - Submits to the shared endpoint: `{restaurant_name: 'General enquiry', city: 'n/a', fsa_id: null, category: 'general', details, reporter_email, page_url: '/contact', website: honeypot}`.
   - Inline JS mirrors the report-card IIFE: validation, 201 → swap form for confirmation, 429 → friendly message, else retry/email fallback. GA4 event `contact_submit`.
   - "Email instead" → `mailto:hello@thaidata.uk?subject=Contact via thaidata.uk`.

**Sitemap:** add `{"loc": "https://thaidata.uk/contact", "priority": "0.8"}` to the curated list in `scripts/generate_sitemaps.py` and re-run it (commit the regenerated sitemap files).

**Tests (extend `tests/test_static_pages.py`):** contact.html exists; has the form ids + honeypot; links /claim/ and /data-quality; `index.html` links `/contact`.

## 5. D3 — endpoint + emails

`functions/api/correction.js`:
- `ALLOWED_CATEGORIES += 'general'`.
- After honeypot: parse `category` first; when `category === 'general'` and restaurant fields are absent, default `restaurant_name = 'General enquiry'`, `city = 'n/a'` (schema columns stay NOT NULL — no migration needed; categories keep the data separable).
- Validation unchanged otherwise (details 10–2000 required for both kinds; email optional).
- Notifications branch on category:
  - Telegram: `✍️ General enquiry #id` vs `🛠 Correction report #id` (distinct verb/icon so inbox scanning is unambiguous), reporter email + page link included.
  - Email subject: `General enquiry — ThaiData UK` vs existing correction subject; hero title `General Enquiry` vs `Correction Report`.
- Retention prune (pro flag): opportunistically `DELETE FROM corrections WHERE created_at < datetime('now','-12 months')` on each submission + `CREATE INDEX IF NOT EXISTS idx_corrections_created ON corrections(created_at)`; mirror in `schema.sql`. This makes the privacy promise true.
- Rate limit unchanged (5/hour/IP shared across both kinds — deliberate: one throttle, one abuse surface).

`functions/api/_email.js`:
- `buildCorrectionNotificationHtml` + `sendCorrectionNotification`: kind-aware subject/hero/labels (category `general` → "General enquiry").
- `sendCorrectionAck`: branch copy — general → "Thanks for your message…"; both kinds gain the reply-window line ("We're a small team — usually within a few hours on weekdays") + /faq link (pro quick win).

`privacy.html`: §1 bullet extended to cover contact messages; §4 retention line now reads "Messages, enquiries and correction reports … deleted within 12 months"; date bumped.

**Tests (extend `tests/test_correction_api.mjs`):**
- general without restaurant_name/city → 201, binds `('General enquiry', 'n/a', 'general', …)`.
- general with too-short message → 400.
- general + valid flow inserts once, attempt recorded.
- existing 10 checks stay green.
